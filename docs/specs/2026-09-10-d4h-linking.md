# Spec: D4H linking & team synchronisation

**Date:** 2026-09-10
**Status:** Phase 1 implemented (branch `worktree-d4h-linking`). Phase 2 (scheduled
sync, §9) deferred. Implementation notes below reflect decisions folded in from
review — see `docs/plans/2026-09-10-d4h-linking.md`.

**Implementation deltas from the original draft:**

- Departed memberships are **archived, not deleted** (`TeamMembership.status:
RecordStatus @default(Active)`; sync toggles `Active` ⇄ `Archived`). A member
  that reappears in D4H is **reactivated**. §7.2 / §7.3 / Appendix B updated.
- `Team_D4H.d4hServer` → **`d4hServerCode`**; `Team_D4H.d4hLastSyncedAt` and
  `Organization_D4H.orgSyncedAt` are both now **`lastSyncedAt DateTime?`** (pure
  sync bookkeeping, never logged, written on every completed sync). `TeamMembership_D4H` has
  **no** `lastSyncedAt`.
- Sync plans are **persisted** (`BatchUpdatePlan`, kind `d4h-team-sync`): preview
  creates the plan row, apply executes that row's items by id with per-item
  preconditions, and one execution per team runs at a time. This replaced the
  original re-plan-and-compare-a-token design (#120, #144, #164) — see
  `docs/plans/2026-10-19-d4h-sync-plans.md`. §6.5, §7 and §8 describe it.
- **Linking no longer syncs.** `linkTeamToD4H` and `createTeamFromD4H` only
  create the links; the first sync is previewed and applied in the sync dialog
  like any other, so manual memberships a link would take over can be reviewed
  first (§6.1, §6.2, §8).
- No `properties.d4h*` backfill (prod/dev count is 0). One schema-only migration.
- `createTeamFromD4H` is a single clean `$transaction` (team management is already
  off better-auth) — Appendix A's orphan-batch caveat no longer applies to it.

**Supersedes:** `importTeamFromD4H` / `syncronizeD4HTeam` in `teams-router.ts`, the
`properties.d4h*` blobs on `Team` / `Person` / `TeamMembership`, and the unused
`TeamType` enum.

This spec covers how AVUT records the relationship between its own
organisations, teams, personnel and team memberships and the corresponding
entities in a D4H Team Manager instance, and how a linked team's membership is
reconciled against D4H on demand.

---

## 1. Background

### 1.1 The two entity models

**D4H side** (read through `openapi-fetch`; Zod schemas in `src/lib/schemas/d4h/`):

| D4H entity     | Identity     | Notes                                                                                       |
| -------------- | ------------ | ------------------------------------------------------------------------------------------- |
| `Organisation` | `id: number` | `title`, `timezone`, `currency`, `reportingStartDay`, `reportingStartMonth`. Owns teams.    |
| `Team`         | `id: number` | `title`; `owner` → Organisation (**optional** in the API — see §5). Detail adds `timezone`. |
| `Member`       | `id: number` | `name`, `email`, `position`, `ref`, `role`, `status`; `owner` → Team.                       |

A D4H `Member` is **not a person** — it is a person _in one team_. D4H has no
cross-team person identity, so the same human on two D4H teams is two `Member`
records with two ids.

Access is per `D4HAccessToken` — either **personal** (`userId` set) or
**organisation** (`userId: null`) — each carrying a `serverCode` of `ap` / `eu` /
`us`. A token's `whoami` lists one `Member` per team the token can see, and a
single token _may_ span more than one D4H organisation.

**AVUT side:**

| AVUT entity      | Current D4H link                                               |
| ---------------- | -------------------------------------------------------------- |
| `Organization`   | none                                                           |
| `Team`           | `Team_D4H` sidecar (declared, **never written by any code**)   |
| `Person`         | `properties.d4hId` JSON blob (a team-scoped member id — wrong) |
| `TeamMembership` | `properties.d4hMemberId` JSON blob                             |

### 1.2 Problems with the current implementation

- **`Team_D4H` is dead.** `importTeamFromD4H` (`@deprecated`) writes
  `properties.d4hTeamId` / `d4hServer` / `d4hLastSync` and never creates the
  `Team_D4H` row, so `syncronizeD4HTeam`'s `if (team.d4h == null)` guard can
  never pass. The sync procedure is unreachable.
- **Mixed sources of truth.** `syncronizeD4HTeam` reads `team.d4h.d4hTeamId`
  (relation) but `team.properties.d4hLastSync` and
  `member.properties.d4hMemberId` (blobs) in the same function.
- **No update path.** Sync only adds and removes memberships; a member whose
  `status` / `position` / `name` changed in D4H is left stale.
- **`d4hId` on the wrong entity.** A D4H member id is team-scoped; storing it on
  `Person` breaks the moment someone is on two D4H teams.
- **Convention drift.** The sync loop issues bare `await`s instead of
  `$transaction([write, logEvent])` pairs.
- **`teams.type` column drift.** Migration `20260404022916_add_team_type` added a
  `type` column (`TeamType`, default `General`); the `Team` model no longer
  declares it. Only the orphaned enum + column remain.

## 2. Principles

1. **A sidecar relation table for every link** — anything sync reads, writes, or
   filters on. `properties` JSON is for free-form user annotation only. (Pattern
   already used by `Team_D4H`, `I3Template_D4H`, `I3TemplateVariant_D4H`.)
2. **An AVUT organisation is in one of three link states:** unlinked; linked to
   exactly one D4H organisation (any number of that org's teams); or linked to a
   single **org-less** D4H team (and nothing else). The three are mutually
   exclusive — see §4, §5.
3. **D4H is authoritative for membership existence and its own snapshot fields.
   AVUT is authoritative for everything else**, including a `Person`'s `name` and
   `email` once the person exists.
4. **Manual, preview-then-apply sync first.** Scheduled sync is Phase 2 (§9).

## 3. Link model

### 3.1 `Organization_D4H` (new — 0..1 per AVUT organisation)

The resolved D4H-organisation identity for an AVUT org, plus a cache of that
org's D4H attributes. **Distinct from `integrations.d4h` settings**, which hold
_policy_ (`enabled`, `teamSync`); this holds _resolved foreign identity + fetched
data_, which does not belong in a JSON config blob.

| Field                    | Type        | Notes                                                                         |
| ------------------------ | ----------- | ----------------------------------------------------------------------------- |
| `organizationId`         | `String`    | `@unique`, FK → `Organization`, `onDelete: Cascade`                           |
| `serverCode`             | `String`    | `ap` / `eu` / `us`. Fixed on first link.                                      |
| `d4hOrganisationId`      | `Int?`      | Set → org-linked mode. `null` while the row exists → org-less-team mode (§5). |
| `d4hOrganisationName`    | `String?`   | Cache                                                                         |
| `d4hTimezone`            | `String?`   | Cache                                                                         |
| `d4hCurrency`            | `String?`   | Cache                                                                         |
| `d4hReportingStartDay`   | `Int?`      | Cache                                                                         |
| `d4hReportingStartMonth` | `Int?`      | Cache                                                                         |
| `syncTokenId`            | `String?`   | FK → `D4HAccessToken` (an org token), `onDelete: SetNull`. Phase 2.           |
| `lastSyncedAt`           | `DateTime?` | Last refresh of the cached attributes above (was `orgSyncedAt`)               |

Created lazily on the first `linkTeamToD4H`.

- **Org-linked mode** (`d4hOrganisationId` set): **sticky** — the id and cached
  attributes survive after the last `Team_D4H` is unlinked, and are cleared only
  by an explicit `unlinkOrganizationFromD4H` admin action (which refuses while
  any `Team_D4H` row remains).
- **Org-less-team mode** (`d4hOrganisationId` null): not sticky — there is
  nothing to cache, so `unlinkTeamFromD4H` of the sole org-less team also
  deletes this row, returning the org to the unlinked state.

### 3.2 `Team_D4H` (exists — extend)

| Field               | Type        | Change                                                                                                               |
| ------------------- | ----------- | -------------------------------------------------------------------------------------------------------------------- |
| `teamId`            | `String`    | `@unique`, FK → `Team`, `onDelete: Cascade` (unchanged)                                                              |
| `d4hTeamId`         | `Int`       | unchanged                                                                                                            |
| `d4hTeamName`       | `String`    | unchanged; refreshed each sync                                                                                       |
| `d4hServerCode`     | `String`    | **renamed** from `d4hServer`                                                                                         |
| `d4hOrganisationId` | `Int?`      | **new** — the team's D4H org; null only if org-less                                                                  |
| `d4hTimezone`       | `String?`   | **new**                                                                                                              |
| `linkTokenId`       | `String?`   | **new**, informational — token that created the link; FK → `D4HAccessToken`, `onDelete: SetNull`                     |
| `lastSyncedAt`      | `DateTime?` | pure sync bookkeeping (was `d4hLastSyncedAt`); the D4H snapshot time of the last completed sync (§7.2), never logged |

### 3.3 `TeamMembership_D4H` (new — replaces `properties.d4hMemberId`)

| Field              | Type      | Notes                                                                     |
| ------------------ | --------- | ------------------------------------------------------------------------- |
| `teamMembershipId` | `String`  | `@unique`, FK → `TeamMembership`, `onDelete: Cascade`                     |
| `d4hMemberId`      | `Int`     | `@index`. The D4H `Member` id — team-scoped, so this is its correct home. |
| `d4hStatus`        | `String`  | `OPERATIONAL` / `NON_OPERATIONAL` / `OBSERVER` / `RETIRED`                |
| `d4hPosition`      | `String?` | Snapshot                                                                  |
| `d4hRef`           | `String?` | Snapshot                                                                  |
| `d4hRoleId`        | `Int?`    | Snapshot                                                                  |

Presence of this row is the marker that a membership is D4H-managed. Memberships
without it were added manually and are never touched by sync.

### 3.4 No `Person_D4H`

D4H has no cross-team person, so there is nothing stable to link a `Person` to.
`Person` identity is `@@unique([organizationId, email])`, and email is the match
key for sync. The `properties.d4hId` currently stamped by `createPerson` in the
sync path is removed.

## 4. Invariants (enforced at link time)

`linkTeamToD4H` resolves the D4H team through the acting token, reads its
`owner` (D4H organisation, or none), and then:

Let the org's current state be one of **(a)** no `Organization_D4H`;
**(b)** org-linked mode (`d4hOrganisationId = Oₓ`, ≥ 1 `Team_D4H`);
**(c)** org-less-team mode (`d4hOrganisationId = null`, exactly 1 `Team_D4H`).

1. **Server consistency.** The token's `serverCode` must equal
   `Organization_D4H.serverCode` if that row already exists; otherwise it is set
   from the token now.
2. **Visibility.** The token must be able to see the D4H team
   (`getD4HTokenMetadata` check, kept from today's `getD4HTeam`).
3. **D4H team has organisation `O`:**
   - **(a)** → create `Organization_D4H` with `d4hOrganisationId = O`, fetch and
     cache `O`'s attributes.
   - **(b)** with `Oₓ == O` → OK. With `Oₓ != O` → **reject**:
     _"This organization is linked to D4H organisation ‹Oₓ›; that team belongs to ‹O›."_
   - **(c)** → **reject**:
     _"This organization is linked to an org-less D4H team, which blocks all other D4H links. Unlink it first."_
4. **D4H team has no organisation (org-less):**
   - **(a)** → create `Organization_D4H` with `d4hOrganisationId = null`. This
     link is now the org's only permitted D4H link.
   - **(b)** → **reject**:
     _"This organization is linked to D4H organisation ‹Oₓ›; an org-less D4H team cannot also be linked."_
   - **(c)** → **reject**:
     _"This organization already has an org-less D4H team linked; only one is allowed."_
5. **One D4H team per AVUT team and vice versa** — `Team_D4H.teamId` is unique;
   a given `d4hTeamId` is linked at most once per AVUT org (enforced in
   application code against the org's teams).

Net effect: an AVUT org holds either N `Team_D4H` rows all under one D4H
organisation, or exactly one org-less `Team_D4H` row, or none. A multi-org token
is handled for free — it may _see_ other D4H orgs; their teams simply cannot be
linked into this AVUT org.

---

## 5. Org-less D4H teams

The D4H API models `Team.owner` as optional, so a D4H team may have no owning
organisation. Supported from Phase 1, with one restriction: **an org-less D4H
team link is exclusive.** If an AVUT org has an org-less D4H team linked, no
other team in that org can be linked to any D4H team (§4.3c, §4.4b, §4.4c).

Rationale: with no D4H organisation there is no shared parent to anchor a "these
teams belong together" guarantee, and no org-level attributes (timezone,
currency, reporting calendar) to cache. Rather than reason about a mixed bag of
unrelated org-less teams, we allow exactly one.

Representation: `Organization_D4H` exists with `d4hOrganisationId = null`; the
single `Team_D4H` row also has `d4hOrganisationId = null`. Unlinking that team
(`unlinkTeamFromD4H`) deletes `Organization_D4H` too — org-less mode is not
sticky (§3.1).

## 6. Operations

All are `organizationProcedure` in `teams-router.ts`. New `operationKey`s
(`d4h-team-link`) are added to the `Operations` registry in `src/lib/operations.ts`.

### 6.1 `linkTeamToD4H({ teamId, d4hTeamId })`

`{ team: ["update"] }`. Links an **existing** AVUT team.

1. Load the team; reject if already linked.
2. Resolve `d4hTeamId` through `getPersonalD4HAccessTokenForUser` +
   `getD4HTokenMetadata`; run §4 invariants.
3. Open a `LogBatch` (`operationKey: "d4h-team-link"`).
4. `upsert` `Organization_D4H` (create + cache attrs, or verify).
5. `$transaction`: create `Team_D4H`, `logEvent` `Update` on `Team`.
6. Return the updated team. Linking imports nobody: the first membership pull
   is a sync (§7) like any other, previewed in the sync dialog and run under its
   own `d4h-team-sync` batch.

### 6.2 `createTeamFromD4H({ d4hTeamId, name? })`

`{ team: ["create"] }`. Convenience for the current import UI: create the AVUT
team and link it, in one `d4h-team-link` batch. Like §6.1 it imports nobody;
the UI opens the new team on its sync preview (§8). `name` defaults to the D4H
team title.

> If team management moves off better-auth (Appendix A), this becomes a single
> `$transaction` for the create + `Team_D4H` + first `logEvent`. Until then it
> carries the same orphan-batch trade-off already documented on
> `importTeamFromD4H` (`auth.api.createTeam` is not a Prisma op).

### 6.3 `unlinkTeamFromD4H({ teamId })`

`{ team: ["update"] }`. Deletes the `Team_D4H` row; `TeamMembership_D4H` rows
cascade away but the `TeamMembership` rows themselves stay (they become
manually-managed). `logEvent` `Update` on `Team`.

- Org-linked mode → `Organization_D4H` is left intact (sticky, §3.1), even when
  this was the last linked team.
- Org-less-team mode → this _is_ the org's only link, so `Organization_D4H` is
  deleted in the same transaction.
- Any `Pending` `d4h-team-sync` plans for the team (§7.1) are marked `Superseded`
  in the same transaction, so a preview left open can't be executed after the
  unlink.

### 6.4 `unlinkOrganizationFromD4H()`

`{ organization: ["update"] }` (or admin). Deletes `Organization_D4H`. Refuses
with `PRECONDITION_FAILED` while any `Team_D4H` row exists in the org.

### 6.5 `createD4HTeamSyncPlan({ teamId })` and `executeD4HTeamSyncPlan({ planId, skipItemIds })`

`{ team: ["update"] }`, both mutations. The two-step preview/apply flow through a
persisted plan — see §7.

- **`createD4HTeamSyncPlan`** rejects a missing team (`NOT_FOUND`), an unlinked
  or archived team (`BAD_REQUEST`), and an org with no usable D4H token
  (`NotConfiguredError`). While another sync of the team is executing it returns
  `{ status: "in-progress" }` without fetching anything. Otherwise it fetches
  both sides, builds the plan, stores it as a `Pending` plan row, and returns
  `{ status: "ready", planId, plan }`. It's a mutation because it writes that
  row, but it writes no `logEvent`: the row is bookkeeping, not a change to any
  record.
- **`executeD4HTeamSyncPlan`** loads the plan by `id` and `organizationId`
  (`NOT_FOUND` otherwise) and applies the stored items under a `d4h-team-sync`
  `LogBatch`, leaving out the items in `skipItemIds`. It needs no D4H token and
  makes no D4H call. Any user with `team: ["update"]` may execute any pending
  plan in the org, not only its creator. It returns
  `{ plan: { id, teamId, payload }, outcomes }`, and throws `CONFLICT` when the
  plan can't be executed (§7.1).

### 6.6 Retirements

- `importTeamFromD4H` — delete; repoint `import-team-from-d4h.tsx` at
  `createTeamFromD4H`.
- `syncronizeD4HTeam` — delete; replaced by §6.5.

## 7. Synchronisation

### 7.1 Shape

```
createD4HTeamSyncPlan(teamId)                  // fetch, build, persist → { planId, plan }
executeD4HTeamSyncPlan(planId, skipItemIds)    // apply that plan's items, no D4H fetch
```

- **`buildD4HSyncPlan(input)` is a pure function** — deterministic,
  unit-testable with no Prisma. Its input is the D4H members, the team's
  memberships (every status, with each person's email), the org's person emails
  split into live and `Deleted`, and the team and org metadata before and as
  incoming.
- **The plan is persisted.** Preview writes it as a `BatchUpdatePlan` row
  (`src/server/services/batch-update-plans.ts`, generic across kinds of bulk
  operation) with `kind: "d4h-team-sync"`, `targetType: "Team"`,
  `targetId: <teamId>`, and the plan as its `payload`. Apply executes **that
  row's items**: it doesn't re-fetch D4H or re-plan, so the user applies exactly
  what they previewed. The payload carries everything execution needs — the
  `d4hTeamId`, the incoming D4H details of each item, the `before` values of
  update and metadata items, and the incoming team and org fields.
- **Each item has a stable `itemId`** (`add:<d4hMemberId>`,
  `update:<teamMembershipId>`, `reactivate:…`, `archive:…`, `relink:…`,
  `metadata`). The user skips items by id.
- **Lifecycle:** `Pending → Executing → Completed | Failed`, or `Superseded`. A
  plan's lock key is `(kind, targetType, targetId)`; the rules below apply only
  among plans with the same lock key, so a D4H sync never blocks a different
  kind of operation on the same team.
- **One execution per team.** Claiming a plan moves it from `Pending` to
  `Executing`, then checks that no other plan for the team is executing. If one
  is, the claim backs off (its plan ends `Superseded`) and the caller gets
  `CONFLICT` ("already running"). Once the check passes, every other `Pending`
  plan for the team is superseded, so an older preview in another tab can't run
  afterwards. Claiming refuses with `CONFLICT` a plan that has already run, has
  been superseded, or has expired.
- **Guards before claiming.** Execute refuses (`CONFLICT`) a plan that isn't a
  `d4h-team-sync` plan on a `Team`, whose team is no longer `Active` or no longer
  D4H-linked, or whose `d4hTeamId` no longer matches the team's link (an unlink
  and re-link elsewhere).
- **Expiry and cleanup.** A `Pending` plan more than 24 hours old can't be
  claimed. An `Executing` plan whose execution started more than 10 minutes ago
  counts as dead — longer than the function timeout — and no longer blocks
  another run. A daily cron (`/api/cron/cleanup-batch-update-plans`, 14:30 UTC)
  marks dead executions `Failed`, then deletes every plan older than 24 hours
  that isn't executing. Completed plans aren't kept as history: the `LogBatch`
  is the record.
- **Per-item preconditions.** Each item re-checks, at execute time, that the
  state it was planned against still holds (§7.3), and records an outcome
  instead of failing the plan: `applied`, `skipped-by-user`, or
  `skipped-changed` with a reason. Items run in the order add, relink, update,
  reactivate, archive, metadata. Items commit one at a time, so an unexpected
  error leaves the plan `Failed` with the outcomes so far and is rethrown; a
  fresh preview picks up the rest.
- **Link and create-from-D4H** (§6.1, §6.2) don't sync. The first sync of a
  linked team goes through the same preview and apply as every later one.

### 7.2 Reconciliation — keyed by `d4hMemberId`

A D4H member is first matched by id against the team's non-`Deleted`, D4H-linked
memberships. One that doesn't match by id is resolved by email (trimmed,
lowercased), through the cases below in order; the first that applies wins.

| Case                                                                                                                   | Action                                                                                                                                                                                                                                                |
| ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| in both, membership `Active`                                                                                           | **update**: diff the `TeamMembership_D4H` snapshot fields (`d4hStatus`, `d4hPosition`, `d4hRef`, `d4hRoleId`). Write + `logEvent` `Update` **only if the diff is non-empty**. `Person` untouched.                                                     |
| in both, membership `Archived`                                                                                         | **reactivate** (`status: Active`), applying any snapshot changes alongside, + `logEvent` `Update`.                                                                                                                                                    |
| not matched by id, blank email                                                                                         | skipped, `missing-email`.                                                                                                                                                                                                                             |
| not matched by id, email shared by several members of the D4H team (#144)                                              | skipped, `duplicate-email` — the email can't pick one person. Members of the same group that _are_ matched by id keep updating as normal.                                                                                                             |
| not matched by id, email belongs to a `Person` in the Rubbish bin                                                      | skipped, `person-in-rubbish-bin`.                                                                                                                                                                                                                     |
| not matched by id, the person's membership on this team is in the Rubbish bin                                          | skipped, `membership-in-rubbish-bin`, so it doesn't fail on every sync.                                                                                                                                                                               |
| not matched by id, the person's membership on this team is linked to a D4H member who is **no longer** in D4H          | **relink** (a member deleted and re-created in D4H): rewrite `d4hMemberId` and the snapshot, reactivating the membership if it's archived, + `logEvent` `Update`. That membership gets no archival.                                                   |
| not matched by id, the person's membership on this team is linked to a different D4H member who is **still** in D4H    | skipped, `linked-to-another-member`.                                                                                                                                                                                                                  |
| not matched by id, otherwise (no membership on this team, or a manual one)                                             | **add**: resolve `Person` by `(orgId, email)` — **reuse if it exists**, else `createPerson`. Create `TeamMembership` + `TeamMembership_D4H`, or take over the person's manual membership (making it D4H-managed and `Active`). `logEvent` either way. |
| AVUT membership **with** a `TeamMembership_D4H` row, `Active`, whose member isn't in D4H and that isn't being relinked | **archive** the `TeamMembership` (`status: Archived`) + `logEvent` `Update`. The `_D4H` row is kept so a reappearance can be detected and reactivated.                                                                                                |
| AVUT membership **without** a `TeamMembership_D4H` row (and not taken over by an add)                                  | never touched.                                                                                                                                                                                                                                        |

Skipped members are listed in the plan with their reason, and the dialog shows
them (§8).

The plan always ends with a **metadata** item that refreshes `Team_D4H`
(`d4hTeamName`, `d4hOrganisationId`, `d4hTimezone`) and, for an org-bearing
team, the `Organization_D4H` cached attributes.

`lastSyncedAt` means "AVUT reflects D4H as of this time". When an execution
completes, `Team_D4H.lastSyncedAt` (and `Organization_D4H.lastSyncedAt` for an
org-bearing team) is set to the plan's `createdAt` — the time of the D4H
snapshot, not the time of the apply. It isn't part of the skippable metadata
item, and a `Failed` execution doesn't change it.

### 7.3 `D4HSyncPlan` shape, preconditions and outcomes

The plan payload, `D4HSyncPlan` in `src/lib/schemas/d4h-sync-plan.ts`
(abridged):

```ts
type Snapshot = {
  d4hStatus: string;
  d4hPosition: string | null;
  d4hRef: string | null;
  d4hRoleId: number | null;
};

type D4HSyncPlan = {
  d4hTeamId: number;
  /** In execution order: add, relink, update, reactivate, archive, metadata. */
  items: (
    | {
        kind: "add";
        itemId: string;
        d4hMemberId: number;
        personName: string;
        email: string;
        incoming: Snapshot;
        personMatch: "existing" | "new";
        adoptsMembership: boolean;
      }
    | {
        kind: "update";
        itemId: string;
        teamMembershipId: string;
        personId: string;
        personName: string;
        d4hMemberId: number;
        before: Snapshot;
        incoming: Snapshot;
        changes: Change[]; /* from diffObject */
      }
    | {
        kind: "reactivate";
        itemId: string;
        teamMembershipId: string;
        personId: string;
        personName: string;
        d4hMemberId: number;
        incoming: Snapshot;
        changes: Change[];
      }
    | {
        kind: "archive";
        itemId: string;
        teamMembershipId: string;
        personId: string;
        personName: string;
        d4hMemberId: number;
      }
    | {
        kind: "relink";
        itemId: string;
        teamMembershipId: string;
        personId: string;
        personName: string;
        previousD4hMemberId: number;
        d4hMemberId: number;
        membershipStatus: "Active" | "Archived";
        before: Snapshot;
        incoming: Snapshot;
        changes: Change[];
      }
    | {
        kind: "metadata";
        itemId: "metadata";
        team: { before: TeamFields; incoming: TeamFields };
        organization: { before: StoredOrgFields; incoming: OrgFields } | null; // null: org-less
        changes: Change[];
      }
  )[];
  skipped: {
    d4hMemberId: number;
    name: string;
    reason:
      | "missing-email"
      | "person-in-rubbish-bin"
      | "duplicate-email"
      | "membership-in-rubbish-bin"
      | "linked-to-another-member";
  }[];
  counts: {
    additions: number;
    relinks: number;
    updates: number;
    reactivations: number;
    archivals: number;
    skipped: number;
  };
};
```

A plan whose only item is a metadata item with no changes is still valid — the
UI shows "already in sync".

**Preconditions**, checked per item at execute time. An item whose precondition
no longer holds is `skipped-changed` with the reason in brackets, and writes
nothing:

- **add:** no membership on this team is already linked to the `d4hMemberId`
  (`already-linked`); the person found by email isn't in the Rubbish bin
  (`person-in-rubbish-bin`); the person's membership on this team, if there is
  one, isn't in the Rubbish bin (`membership-in-rubbish-bin`) and isn't linked
  to another D4H member (`linked-to-another-member`). A lost race with a
  concurrent manual add takes over the membership the other request created.
- **relink:** the membership still exists (`membership-missing`), isn't in the
  Rubbish bin (`membership-in-rubbish-bin`), is still linked to
  `previousD4hMemberId` (`d4h-member-changed`), and no other membership on the
  team is linked to the new id (`already-linked`).
- **update:** the membership still exists, isn't in the Rubbish bin, is still
  linked to the same `d4hMemberId`, and its stored snapshot still equals
  `before` (`details-changed`).
- **reactivate:** the membership is still `Archived` (`not-archived`) and still
  linked to the same `d4hMemberId`.
- **archive:** the membership is still `Active` (`not-active`) and still linked
  to the same `d4hMemberId`.
- **metadata:** each field is written only while its current value still equals
  `before`; the others are left alone and listed as `skippedFields`
  (`Organization_D4H` is shared across teams). The item is `skipped-changed`
  (`fields-changed`) when no field is left to write.

**Outcomes** are stored on the plan row, one per item:
`{ itemId, result: "applied" | "skipped-by-user" | "skipped-changed", reason?, skippedFields? }`.

### 7.4 Writes & logging

- Every write is paired with its `logEvent` inside `$transaction([...])` (fixes
  the current bare-`await` drift). One `$transaction` per member is acceptable —
  they are independently meaningful events (per `operations.ts` guidance) and the
  loop is bounded by team size.
- One `LogBatch` per execution, `operationKey: "d4h-team-sync"`,
  `userId = ctx.userId`, the first sync after a link included. The link itself
  writes its entries under a `d4h-team-link` batch. The plan row stores its `logBatchId`. Plan rows themselves
  aren't audited: creating, claiming, superseding and finishing a plan write no
  `logEvent`, like `lastSyncedAt`.
- `logEvent` entries carry `refs` to `Person` and `Team` as `context`, matching
  the existing pattern in `importTeamFromD4H`.

### 7.5 Authority

- **D4H authoritative:** whether a membership exists; `d4hStatus`, `d4hPosition`,
  `d4hRef`, `d4hRoleId`; team `title` / `timezone` / owning org.
- **AVUT authoritative:** `Person.name`, `Person.email` (once the person
  exists), `Person.tags` / `properties`; `TeamMembership.tags` / `properties`;
  all skill-tracking data; manually-added memberships.

## 8. UI

- **Team detail page** gains a "D4H" card (behind `integrations.d4h.enabled` and
  `Protect team:["update"]`):
  - unlinked → "Link to D4H…" opens a dialog listing token-visible D4H teams
    (`d4hApi.listTeamsAccessibleToUser`), applying §4 rejections inline. A
    successful link replaces it with the sync dialog, so the first import is
    previewed.
  - linked → shows `d4hTeamName`, D4H org, `lastSyncedAt`, a "Sync…" button
    and an "Unlink" menu item.
- **Sync dialog** (`?action=d4h-sync`, per `mutation-dialog.md`): calls
  `createD4HTeamSyncPlan` once on open, and lists the plan's items grouped by
  kind (additions, re-links, updates, reactivations, archivals, metadata) and
  its skipped members grouped by reason. The user can skip individual items;
  "Apply" calls `executeD4HTeamSyncPlan` with the plan's id and the skipped
  `itemId`s.
  - When the server returns `in-progress`, the dialog says "A sync of this team
    is running", disables Apply, and re-polls every few seconds.
  - While Apply is pending the dialog can't be dismissed, and reopening it
    doesn't reset the in-flight mutation.
  - A `CONFLICT` on execute (already run, superseded, expired, already
    running) shows its message and lets the user refresh the preview, which
    creates a new plan.
- **Create-from-D4H** replaces the current import dialog wiring, calling
  `createTeamFromD4H`, then navigates to the new team with its sync dialog open
  (`?action=d4h-sync`).
- **Admin → Organization page** gains a read-mostly "D4H Integration" card
  (behind `integrations.d4h.enabled` and `Protect organization:["update"]`),
  shown only when an `Organization_D4H` row exists — it is created as a
  by-product of the first team link and is never user-created, so there is no
  "Link" action. Surfaces the bound D4H organisation (name + id, or "org-less"),
  server, cached timezone / currency / reporting-year start, linked-team count
  and `lastSyncedAt`. Actions live both on the card and in a `⋮` menu beside the
  page's Settings button (which also carries Edit and a placeholder Delete):
  - **Sync** — `syncOrganizationD4H`, refreshes the cached org attributes from
    D4H (metadata only; membership sync stays per-team). Shown only for an
    org-linked link with ≥1 linked team (needs a team for D4H API context).
  - **Unlink** — `unlinkOrganizationFromD4H`, disabled with an explanation while
    any `Team_D4H` remains.
    Backed by a `teams.getOrganizationD4H` query. There is no org-level "Link"
    action — the `Organization_D4H` row is only ever created as a by-product of
    linking a team.
- **D4H action visibility** (team menu + org menu/card): actions that don't
  apply to the current link state are hidden, not disabled — no Sync/Unlink when
  unlinked, no Link when linked.

## Appendix A — team management off better-auth (recommendation, not scoped here)

AVUT uses better-auth's organization-plugin team mechanism (`auth.api.createTeam`
/ `removeTeam`, the `TeamUser` join, `Team.memberCount` and
`TeamUser.membershipKey` maintained with `input: false`). In practice AVUT does
its own team membership through `Person` + `TeamMembership` and gets little from
the plugin's team layer beyond friction:

- `createTeam` / `removeTeam` are not Prisma ops, so they cannot join a
  `$transaction` with the `logEvent` — every team mutation carries an
  orphan-row / partial-failure caveat (see `createTeam`, `deleteTeam`,
  `importTeamFromD4H`).
- `TeamUser` / `memberCount` / `membershipKey` duplicate state AVUT does not read.

**Recommendation:** manage `Team` directly through Prisma (`create` / `update` /
`delete` in a `$transaction` with `logEvent`), drop `TeamUser` and the
`input: false` columns, and keep `Team` purely as an AVUT-owned record. This
removes every orphan-batch caveat, including from `createTeamFromD4H`.

Track as a separate change; this spec does not depend on it but is cleaner with
it.

## Appendix B — resolved decisions

| Question                           | Decision                                                                                      |
| ---------------------------------- | --------------------------------------------------------------------------------------------- |
| `Person` name/email after creation | AVUT authoritative — sync never overwrites                                                    |
| Removed memberships                | archived (not deleted); reappearance reactivates                                              |

| Email collision on create          | reuse the existing `Person`                                                                   |
| Sync UX                            | preview a persisted sync plan → user applies it by id, skipping items if they choose          |
| Scheduled sync                     | Phase 2, deferred                                                                             |
