## Background

Members are invited to training in D4H and leave their attendance at `REQUESTED` until the last minute, so team leadership chases them by hand. This module runs admin-configured reminder rules on an hourly schedule. Each rule looks at one AVUT team's linked D4H team, finds Exercises starting soon, and emails every member whose attendance is still `REQUESTED`. Every email carries an opt-out link.

Along the way the branch adds two settings the module needs:

- **Reply-To** (org-level) for every email the org originates, since replies to `no-reply@mx.avut.nz` reach nobody.
- **The module's D4H token**: which org-owned D4H access token the module's unattended runs use, chosen in the module's own settings. `Organization_D4H.syncTokenId` (for a future scheduled team sync) and the old `integrations.d4h.syncToken` setting both exist, but nothing reads either today. The old setting is only cleaned up on token delete (`d4h-access-tokens-router.ts` ~L298). This branch uses neither.

What exists already, and what doesn't:

- `getOrganizationD4HAccessToken({ organizationId, tokenId })` (`src/server/d4h-access-token.ts:110`) resolves an org-owned token with no session. Only dev token pages use it today.
- No D4H call runs from a cron yet. The cron pattern is `src/app/api/cron/purge-rubbish/route.ts` (a `CRON_SECRET` bearer check) → binder in `src/server/cron/` → a service that takes `prisma`. Unattended audit logging is `createLogBatch` + `unattendedOrgContext` (`src/server/services/service-context.ts:89`), as in `Trash.runAutoPurge` (`trash.ts:531`).
- `src/server/d4h-api/client.ts` has no function that lists exercises, lists attendance by activity, or fetches members by id. Attendance and team-detail paths need `d4hGetWithUntypedPath` (client.ts:238). The established way to fetch a whole list is one request with `size: 10000` (`src/server/d4h-api/equipment.ts`), not a page loop.
- `D4HMember.schema` is strict about `email`. `D4HMemberWithOptionalEmailSchema` (client.ts ~L254) maps a null or missing email to `email: null`, and is what member lookups outside team sync use.
- D4H web-app URLs are built from the team's **subdomain**: `d4hEquipmentItemViewUrl(serverCode, subdomain, itemId)` in `src/lib/d4h-servers.ts` → `https://<subdomain>.<teamManagerHost>/team/equipment/view/<id>`. The subdomain comes from `fetchD4HTeamDetailCached` (as in `d4h-tasks-router.ts` ~L123–140).
- `sendEmail` (`src/server/email.ts`) swallows errors and returns `void`, so a caller can't tell a failed send.
- There's no long-random-token helper (`src/lib/id.ts` has only nanoids and UUIDs).
- `/public` is already a public prefix in `src/proxy.ts`, with no routes under it yet. The invitation landing page (`src/app/(public)/invitations/`) is the prior art for a public page backed by `publicProcedure` (`invitations.getLanding`, `invitations.signUp`).
- Org modules can declare `requires` (`d4h-i3` requires `d4h`), enforced by `isModuleUsable`, the settings write path (`enforceModuleRequirements`) and `Feature_SettingsCard`.

## Decisions

**Settings**

1. **Reply-To** is `general.replyTo` in `OrganizationSettings`: `z.email().nullable().default(null)`, in the same shape as `integrations.d4h.syncToken`. It's stored as `OrganizationConfig` rows, so no migration. It's edited from a row on the General settings card.
2. Reply-To applies to every org-originated send:
   - the organization invitation (`sendInvitationEmail`, `src/server/auth.ts` ~L258)
   - I3 issue: the `NotifyPersonnel` stage (through `I3Notifications.sendEach`) and the `SendReceipt` stage in `src/forms/i3-issue-items/processor.ts`
   - I3 return: the same two stages in `src/forms/i3-return-items/processor.ts`
   - the d4h-nag reminder

   It never applies to the verification code or the email-changed notice (`auth.ts` ~L149/L182).

3. **The module's D4H token** is `modules.d4h-nag.d4hTokenId` in `OrganizationSettings` (`z.string().nullable().default(null)`). It's stored as `OrganizationConfig` rows, so no migration. It's picked from a "D4H token" row on the module's settings card in org settings, and is configured for this module only.
   - The picker offers only org-owned D4H credentials (`userId: null`) whose `serverCode` matches `Organization_D4H.serverCode`.
   - The generic slice write doesn't validate the id, so the resolver checks it at use time. Anything that isn't an org-owned D4H credential of this org counts as no token. A token on the wrong server shows up as `token-cannot-see-team`.
   - Deleting the token clears the setting, the same way `deleteOrganizationAccessToken` already clears `integrations.d4h.syncToken`.
   - `Organization_D4H.syncTokenId` is left alone for a future scheduled team sync. Removing the dead `integrations.d4h.syncToken` key is parked, not done here.

**Rules**

4. A rule belongs to an AVUT `Team`. Its D4H team comes from the team's `Team_D4H` link at run time; nothing D4H-side is copied onto the rule. A team can have any number of rules.
5. Rule fields: `teamId`, `weekday` (0–6, Sunday = 0, as `Date.getDay()`), `hour` (0–23), `lookAheadHours` (1–168, default 24), `message` (optional, plain text, ≤ 1000 chars), `enabled`. Times are in the org's `general.timeZone`. The rule has no `@updatedAt`: the slot claim (decision 8) writes the row every week, so the last-edited time comes from the audit log instead.
6. A rule is **runnable** only when all of these hold; otherwise the rule list shows the first one that fails as a paused reason:
   - the org's D4H integration is on (`integrations.d4h.enabled`, the switch every other D4H path checks): `d4h-disabled`
   - the rule is enabled: `disabled`
   - its team is `Active` (Archived and Deleted both fail): `team-inactive`
   - its team is linked to D4H: `team-unlinked`
   - the module has a D4H token that resolves to one of this org's own D4H credentials: `no-token`
   - that token's cached metadata (`getD4HTokenMetadata`) lists the team's `d4hTeamId`: `token-cannot-see-team`

   Module usability (decision 26) is checked separately. The cron skips paused rules silently, and **Run now** refuses with the reason.

7. Deleting a rule is a hard delete that **keeps its history**:
   - `D4HNagRun.ruleId` is nullable with `onDelete: SetNull`.
   - Each run carries its own `teamId` (FK, cascade) and a cached `teamName`, so recipient rows, dedupe keys and opt-out tokens never depend on the rule.
   - A run whose rule is gone shows as "Deleted rule".
   - Rules aren't Rubbish-bin entities.

**Scheduling**

8. One dispatcher at `/api/cron/d4h-nag`, scheduled `"0 * * * *"` in `vercel.json` (the project is on Vercel Pro).
   - Each tick, for every runnable rule, it computes the rule's latest slot at or before `now`: that weekday and hour in the org's timezone, DST-safe.
   - If the slot is later than `rule.lastScheduledFor`, it claims the slot atomically and runs the rule. The claim is `updateMany where lastScheduledFor is null or < slot` returning count 1, so a slow tick can't overlap the next one.
   - **Stale slots:** creating a rule, enabling it, or changing its `weekday` or `hour` sets `lastScheduledFor = latestSlot(now)`, so a slot that has already passed never fires because of an edit.
   - **Retry:** a scheduled run that fails before sending anything (a D4H error, or the token going) puts `lastScheduledFor` back to its previous value, so the next tick retries. A run that fails after some sends keeps the claim; dedupe makes a retry safe anyway, but a partial run is better looked at than repeated blindly.
9. **Catch-up** falls out of (8): a missed tick is picked up by the next one, because the latest slot is still unclaimed. Only the latest slot is considered, never a backlog.
10. **Window:** a scheduled run looks at exercises starting in `[max(now, slot) + 1h, slot + lookAheadHours]`. A manual run uses `[now + 1h, now + lookAheadHours]` and doesn't touch `lastScheduledFor`. The `+1h` is the "too close to be useful" guard. An empty window (lead time already passed) still records a run with zero exercises.
11. Exercises only, filtered by `starts_after` + `before` on `/exercises`. `after` means _ends_ after, which is wrong here. Like `myActivitiesToday`, there's no `published` filter; check during the build whether unpublished exercises ever carry `REQUESTED` attendance. Exercise title uses the same rule as `buildD4HToday` (`src/lib/d4h-today.ts:90`): `referenceDescription ?? reference ?? "Untitled exercise"`.
12. **Stuck runs:** each tick first marks any run still `Running` after 15 minutes as `Failed` ("Timed out"). It also clears the `dedupeKey` of that run's `Pending` rows without a `tokenHash` and marks them `Failed`, so the members can be retried. A `Pending` row with a `tokenHash` may have been sent, so it keeps its claim.

**Recipients**

13. Recipients are attendance records for those exercises with status `REQUESTED` (`activity_id[]` + `status=REQUESTED` on `/attendance`). The email comes from the D4H member record, fetched with `id[]` for just those members, not the whole team, and parsed with the optional-email member schema. There is no AVUT `Person` lookup. "No email" means `email === null` or a blank `value` after trimming; that member is `SkippedNoEmail` and never fails the run. Unverified addresses are still used, since D4H itself emails them.
14. **Once per (org, D4H team, exercise, member), across all rules.**
    - A recipient row carries `dedupeKey = "<organizationId>:<d4hTeamId>:<exerciseId>:<memberId>"` with a unique index (Postgres allows many NULLs). Including the org means two orgs linked to the same D4H team never suppress, or reveal, each other.
    - **Claim:** the runner creates the row with the key set, outcome `Pending` and the opt-out link's `tokenHash`. A P2002 there means `SkippedAlreadyReminded`.
    - **Send:** the runner sends, then updates the row to `Sent`, or to `Failed` with the key cleared so a later run can retry.
    - **Dry runs** never set the key. They look it up (`findUnique`) and record `SkippedAlreadyReminded` when a claim exists.
15. Outcomes:
    - `Pending`: claimed, send in progress; on a finished run, sent but unconfirmed (the email went out, or may have, but `Sent` was never recorded, so the claim is kept)
    - `Sent`, `Failed`
    - `SkippedNoEmail`, `SkippedOptedOut`, `SkippedAlreadyReminded`
    - `DryRun`: would have sent

    A dry run records every outcome except `Pending`, `Sent` and `Failed` as it would for a real run.

16. Sends go out one at a time, at least 500 ms apart (a constant in the runner), to stay under Resend's per-second limit. The cron route exports `maxDuration = 300`. All orgs share that one invocation, so the budget (about 500 emails per tick) is shared too, which is still well above real use (a team of ~60 with two exercises is ~120 sends, ~1 minute). A run cut off by the limit is cleaned up by decision 12.
17. `sendEmail` returns `{ ok: true } | { ok: false; error: unknown }`. It still never throws. Existing callers ignore the result.
18. **Run now / Dry run run in the background.** `runRule` creates the `D4HNagRun` row (`Running`) inside the request, returns its id, and finishes the fetch and send loop in `after()` (from `next/server`). The UI navigates straight to the run, which refetches while it's `Running`. `after()` work counts against the invoking function's duration, so before building, read `after()` in `node_modules/next/dist/docs/` and check the tRPC route's `maxDuration` covers a run (raise it there if not). A run that `after()` drops is cleaned up by decision 12.

**Opt-out**

19. Rows are keyed on (AVUT team, D4H member id), unique, with the member's name cached for display. A row exists means opted out. Opting back in deletes the row. Fields record who made it: `createdById` null and `source: Self` for the member, or the admin's user id and `source: Admin`.
    - **Scope at run time:** a member is `SkippedOptedOut` if an opt-out exists for them on **any** AVUT team in this org currently linked (through `Team_D4H`) to the rule's `d4hTeamId`. Several AVUT teams can link to one D4H team; "stop sending me these" means all of them. An opt-out on a team that's since been relinked elsewhere simply stops matching.
20. **Link tokens:**
    - Each `Sent` recipient row gets a random token, `randomBytes(32).toString("base64url")`, from a new `src/server/link-token.ts`. `DryRun` rows get none, since their plaintext would never reach anyone.
    - The row stores only `tokenHash` (sha256 hex, unique). The token appears only in the email.
    - The opt-out link is `${baseUrl}/public/d4h-nag/opt-out/<token>` (`baseUrl` from `src/emails/base-url.ts`).
    - It stays valid until the row is purged (decision 23), and survives the rule being deleted (decision 7).
    - The same token will carry the stage 2 respond page.
21. The public page is `src/app/(public)/public/d4h-nag/opt-out/[token]/page.tsx`. It shows the org, the team, the member's name and their current state, with one button that POSTs (a `publicProcedure` mutation). A GET never changes state, because email link scanners open every URL. It shows nothing else from D4H (see d88a718e).
22. A self-service opt-out or opt-in is audited with a `LogBatch` (`operationKey: "d4h-nag-opt-out"`), because `recordLogEntry` requires a batch when there's no actor. Its `actorLabel` is the member's cached name, and the entry is `Create`/`Delete` on `D4HNagOptOut`. Admin edits go through `ctx.logEvent` as usual.

**Runs, audit and retention**

23. Run and recipient rows older than 90 days (by `startedAt`) are deleted by the d4h-nag dispatcher at the end of each tick, **for every org**, including orgs that have turned the module off. Recipients cascade with their run. This replaces the issue's "via purge-rubbish": that job is about the Rubbish bin, and keeping the prune with the module keeps it self-contained (agreed in planning). Opt-outs are never pruned.
24. A run's completion writes `sentCount`, `skippedCount` and `failedCount` onto the run, so the runs table doesn't need a `groupBy`.
25. Each real (non-dry) run opens a `LogBatch` (`operationKey: "d4h-nag-run"`; actor null with `actorLabel: "D4H attendance reminders"` for cron, the user for Run now). It writes one entry: action `Run` (new) on `D4HNagRule`, with a description summarising exercises and outcome counts.
    - Dry runs write no audit entry, since they change nothing but their own run record.
    - The `d4h-nag-run` and `d4h-nag-opt-out` `Operations` entries each get a comment saying they open a single-entry batch for provenance, not to group several events.
    - Rule create, update and delete, and admin opt-out add and remove, use `ctx.logEvent` paired in `$transaction`. New `LogObjectType`s: `D4HNagRule`, `D4HNagOptOut`, both mapped to `"d4h-nag"` in `moduleByObjectType` (`src/lib/schemas/log-entry.ts:210`). New `LogAction`: `Run`.

**Module and permission**

26. Module `d4h-nag` (label "D4H Attendance Reminders", icon `BellRingIcon`, segment `d4h-nag`), with `requires: "d4h"` (like `d4h-i3`) and a `modules.d4h-nag.enabled` setting (default `false`). It's behind a new Vercel flag `d4h-nag-module` (`src/lib/flags.ts`, default `false`), listed in `FLAGGED_MODULE_IDS` (`src/lib/module-flags.ts`) and `MODULE_FLAG_EVALUATORS` (`src/server/module-flags.ts`), like `notes`.
27. The cron decides which orgs to process from settings alone: `modules.d4h-nag.enabled` **and** the requires chain (`modules.d4h.enabled`), using the same helpers `isModuleUsable` uses (`enabledInSettings` + `requiredModuleOf`), but not the Vercel flag. The flag hides the settings card, so the setting can't be turned on while the flag is off. Evaluating flags outside a request isn't something the codebase does yet.
28. New permission statement `d4hNag: ["view", "update", "run"]`, granted in full to `owner` and `admin` only. `view` covers rules, runs and opt-outs; `update` covers rule and opt-out changes; `run` covers Run now and Dry run. The sidebar hides the module from callers without `d4hNag: ["view"]`, as `OrgSidebar_Modules` does for Skill Track.
29. **Email:** a new React Email template `src/emails/d4h-attendance-reminder.tsx`, in the style of `organization-invite.tsx`. It's from `NoReplyEmailAddress` with the org's Reply-To. Subject: `Are you coming to <exercise>? <Mon 3 Nov, 7:00 pm>`. The body has:
    - the org and team name
    - the exercise title and start (org timezone)
    - the rule's message, if set
    - a prompt to update attendance in D4H
    - a link to the exercise in D4H via `d4hExerciseViewUrl(serverCode, subdomain, exerciseId)` (Task 6), if the user confirms the path
    - the opt-out footer
30. The marketing page (`src/app/(public)/(marketing)/page.tsx`) gets a `MODULE_COPY` entry for `d4h-nag` (it's `satisfies`-tied to the org module ids) and the id in `NEEDS_D4H`. Proposed copy: "Email members who haven't answered their D4H training invitation, on a schedule you set."
