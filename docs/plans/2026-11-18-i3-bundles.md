# D4H I3 bundles: standard-issue kit definitions with a held/missing comparison

**Date:** 2026-11-18
**Issue:** [#518](https://github.com/redcloud-nz/avut/issues/518) (milestone v0.13 - nucula), from
[redcloud-nz/avut-ideas#39](https://github.com/redcloud-nz/avut-ideas/issues/39)
**Branch:** `feat/i3-bundles`, worktree `.claude/worktrees/i3-bundles`
**DB:** adds a migration. `npm run db:branch i3-bundles` before Task 1's `migrate dev` (it needs
every connection to `avut` closed), and `npm run db:unbranch` once merged.
**Written against:** integration @ 6e730e37

A bundle is an organisation's named list of I3 templates that make up a standard issue
("Recruit", "Responder"). From a bundle you compare it against a D4H team's members and see, for
each member and each template in the bundle, whether they hold an item of it or are missing it.
This is the first, pre-tags slice of the kit-check idea. Data-quality states (incomplete / doesn't
match) come in [#519](https://github.com/redcloud-nz/avut/issues/519).

## Decisions

- **A bundle** has `name`, `description`, `status` (`RecordStatus`: delete/recover through the
  Rubbish bin like templates; no archive) and a set of templates. Its lines are a plain set (no
  order, notes or quantity), shown by template category title, then template name.
- **Bundle lines are a join table** `I3BundleItem` keyed by `(bundleId, templateId)`, cascading
  from both sides. A template that is **soft-deleted** keeps its line, which shows flagged
  "Deleted template" and is left out of the comparison, then comes back as it was when the
  template is recovered. Purging a template from the Rubbish bin removes its lines (cascade),
  silently: no entry on the bundle. That's deliberate, not a missing log entry.
- **The bundle pages need no D4H token to define and edit a bundle.** Only the comparison pages
  read D4H. The bundle page reads D4H only through `D4HTeamPickerDialog`, which queries once
  it's opened.
- **`updatedAt` covers line changes too:** `addTemplates`/`removeTemplate` touch the bundle row
  (`updatedAt: new Date()`) in the same `$transaction` as the line write and its log entry.
- **A template with no D4H type** (`I3Template.d4h` is `null`) can't be matched against D4H. The
  add-templates picker offers only Active templates with a D4H type that aren't already in the
  bundle. A line whose template has lost its D4H type shows flagged "No D4H type" and is left out
  of the comparison, the same as a deleted one.
- **Permissions:** a new `i3Bundle` resource, `["view", "create", "update", "delete"]`. `i3-admin`
  gets all four, `i3-editor` gets `view`. As with `i3Template`, `owner`/`admin` get nothing
  extra. Adding or removing a line is `update`. The comparison also needs `d4hEquipment: ["view"]`
  (it reads D4H through the existing `d4hApi` queries), which both I3 roles already hold.
- **Audit log:** a new `LogObjectType` `"I3Bundle"`, attributed to `d4h-i3`. Create, Update,
  Delete and Recover log on the bundle like templates do (`diffObject` changes on create/update).
  Adding or removing templates is an `Update` on the bundle, one entry per mutation, with a
  `description` naming the templates added or removed and a `context` ref to each template. The
  refs are for when templates get a History page; `I3Template` has none today.
  `RelatedEntryPermissions` gets `I3Bundle: { i3Bundle: ["view"] }`.
- **A new router** `i3Bundles` (`src/trpc/routers/i3-bundles-router.ts`) over a new service
  `src/server/services/i3-bundles.ts`, not more procedures on the 500-line `i3Router`.
- **The comparison is computed on the client** from queries that already exist, by one pure
  helper, `src/lib/i3-bundle-compare.ts`:
  - the bundle and its lines (`i3Bundles.getBundle`, which includes each line's template with its
    `d4h` and `status`);
  - the team's members (`d4hApi.listTeamMembers`: Operational and Non-operational members);
  - the team's issued items with their holders (`d4hApi.listTeamIssuedEquipment`: one team-level
    D4H request, not one per member).

  No new D4H-token procedure. #519 will extend the same helper with its third state.

- **What "held" means:** the member holds at least one item whose `kind.id` equals the line
  template's `d4h.kindId`, any brand or model, and whose `status` is not `LOST` or `RETIRED`. A lost
  item doesn't count, because the member doesn't have it, but the helper keeps it on the missing
  cell (`lost`) so the member page can say "1 item marked Lost". The RETIRED filter is defensive:
  the list is fetched with `only_current`. Two templates on the same D4H type both match the
  same item; that's accepted for v1.
- **Lines that don't fit the team are excluded, not missing.** A kind can be owned by one D4H
  team (`src/lib/i3-template-fit.ts`). Comparing against a team whose catalogue lacks it would
  show everyone missing. The comparison prefetches `i3.listTemplateFits({ teamId })` (needs
  `i3Item: ["issue"]`, held by both I3 roles), and a line whose template isn't in its
  `templateIds` is excluded with reason `"not-in-team"` ("Not used by this team").
- **Known v1 limit:** `listTeamIssuedEquipment` keeps only items the team owns, so a member
  holding an item owned by another team shows missing for it. Issued Types has the same limit.
  The help card says so.
- **Who is shown:** every member `listTeamMembers` returns, sorted by name. No filtering in v1.
  An item whose holder isn't in that list (e.g. a retired member) isn't shown.
- **Team choice** goes through `D4HTeamPickerDialog` over `listAccessibleTeams`, the same source
  Issued Types uses. Don't add any scoping here. #468 was closed as superseded (2026-11-18) by
  team scope (#520). D4H and I3 stay in org scope for now, so there's nothing to rebase onto. #530
  (org templates limited to D4H-organisation-owned records) may later narrow which templates
  can be added; the fit-based `"not-in-team"` exclusion covers either outcome.
- **Routes**, all under the d4h-i3 module:
  - `/orgs/[slug]/d4h-i3/bundles`: the list.
  - `/orgs/[slug]/d4h-i3/bundles/[bundle_id]`: a bundle, with its lines and a **Compare** action.
  - `/orgs/[slug]/d4h-i3/bundles/[bundle_id]/teams/[d4h_team_id]`: the matrix.
  - `/orgs/[slug]/d4h-i3/bundles/[bundle_id]/teams/[d4h_team_id]/members/[member_id]`: one
    member's comparison.
- **Help:** one shared card `content/help/d4h-i3/bundles.mdx` for all four bundle screens, with
  a `<HelpButton>` on each. The module card `content/help/d4h-i3.mdx` gets a **Bundles** bullet.
  The card's `guide` is `d4h-i3` until `/avut-docs` writes a bundles guide.

- [x] **Task 5: Comparison helper** (feat(i3): add the bundle comparison helper)
  - **Files:** `src/lib/i3-bundle-compare.ts` (new), `src/lib/i3-bundle-compare.test.ts` (new).

    `compareBundle({ lines, members, items, fittingTemplateIds })`:

    - `columnTotals`: how many members hold each column.

    Match on `item.kind.id === line.template.d4h.kindId` and `item.holder.id === member.id`, and
    ignore items whose `status` is `LOST` or `RETIRED`. Export the state type so #519 can widen
