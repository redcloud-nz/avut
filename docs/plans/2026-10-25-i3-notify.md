## Decisions

- **Settings shape.** `modules.d4h-i3.notify = { org: PersonId[], teams: Record<TeamId, PersonId[]> }`, defaulting to `[]` and `{}`.
  - **Why a record.** `flatten` (`settings-schema.ts`) recurses into plain objects, so each team is its own config row, `modules.d4h-i3.notify.teams.<teamId>`, holding a scalar array. That is the only array shape `diffObject` (`src/lib/diff.ts`) accepts, and the audit log then records changes per team. An array of `{ teamId, personIds }` objects was tried first, and it makes every org-settings write throw `DiffValueError` (user decision, 2026-10-25).
  - **Storage fixes that come with it.**
    - `writeWith` (`settings-store.ts`) only walks keys in the next settings, so a team key that drops out would keep its row and come back on the next read. It now also deletes rows for keys in the existing settings that are missing from the next settings. The existing settings are schema-parsed, so only dynamic record keys can disappear this way.
    - These are the first array leaves in any settings tree. `writeWith` compares leaves with `!==`/`===`, which for arrays means every `modules.d4h-i3` save (even the Enable toggle) upserts them, and a `[]` equal to the default never deletes its row. Switch both comparisons to `R.isDeepEqual`.
- **Editing and logging.** `notify` lives in the existing `modules.d4h-i3` slice, so whoever can edit org settings (`organization: ["update"]`) edits it, and the existing settings mutation does the audit logging. A slice patch is partial only one level down, so `notify` is always saved whole.
- **Team key.** The list is keyed by AVUT `TeamId`, not the D4H team id. The processors get `recipient.teamId` as a D4H team id and look up the org's AVUT team(s) through `Team_D4H.d4hTeamId`. `Team_D4H` is unique per AVUT team only, so allow several.
- **Hidden entries survive a save.** The dialog shows only Active, D4H-linked teams, but on save it carries over every `teams` entry it isn't showing (an unlinked, archived or deleted team). A re-linked team then gets its list back. Teams with an empty list are dropped on save.
- **One list per scope.** Issue and Return notify the same people.
- **Union.**
  - The recipients are the org list plus the lists of the matched teams that aren't Deleted.
  - Only `Active` people in the org are kept. Ids that no longer resolve are dropped without an error, and so are people with an empty email.
  - Duplicates are removed by `PersonId`. `Person` is `@@unique([organizationId, email])`, so that's enough.
  - An empty result means no notification is sent.
- **One email per recipient**, not one email with everyone in `to`. The templates' footer says "This email was sent to {emailTarget.email}", and per-recipient sending keeps addresses private.
- **Receipt address.** The receipt goes to the D4H member's email, fetched with `GET /v3/team/{d4hTeamId}/members/{member}` at send time. A missing member, an empty email or a failed fetch skips the receipt with a log line.
- **The Issue receipt goes out even if D4H recording failed.** `CreateEquipmentInD4H` never throws and reports failures in `savedToD4H`. The receipt records a physical handover, which happened regardless.
- **Email never fails the form.** `sendEmail` (`src/server/email.ts`) catches and logs its own errors and never rejects. What can throw in these stages is the resolver's DB and settings reads and the D4H member fetch. So each notify and receipt stage is wrapped in one try/catch that logs and carries on.
- **All mail through `sendEmail`**, so outside production it still goes to Resend's sink.
- **Settings reads in the processors** use `OrgSettings.read(ctx.prisma, ctx.organizationId)` (the uncached service), not the `"use cache"` wrapper, so a just-saved list applies to the next submission.
- **No D4H token.** `CheckD4HAccessToken` throws before the notify and receipt stages run. The resolver needs no token. The settings UI reads D4H links only from `Team_D4H` in the DB (through `listTeams`), so it works without a token.
