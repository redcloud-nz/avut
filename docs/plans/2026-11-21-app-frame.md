## Decisions

### Help from the route (#560)

- **Cards list their routes in frontmatter:** `routes: ["/orgs/[slug]/admin/teams", "/orgs/[slug]/admin/teams/[team_id]", …]`. These are typed-route patterns, written as the path under `src/app/` minus route groups, the same patterns `route()` takes.
- **Exact patterns only, no subtree wildcard.** Each page a card covers is listed. It keeps the coverage test meaningful (a new page has to be placed on purpose) and the matcher small. `d4h` lists 15 routes; that's fine.
- **Matching:** a pattern matches a pathname when the segment counts are equal and every static segment is equal; `[param]` matches any one segment. There are no catch-all or intercepting routes under `(authenticated)` (`@modal` holds only `default.ts`; `--update` is a plain static segment), so the matcher throws on `[...x]`, and adding one later is a deliberate change.
- **Most specific wins:** compare matching patterns segment by segment, and a static segment beats `[param]` at the first difference (`/admin/teams/new` beats `/admin/teams/[team_id]`). Two cards listing the same pattern is a test failure, not a tie-break.
- **The card list reaches the button through context, not by importing `allHelpCards` on the client.** `allHelpCards` carries each card's compiled MDX, which the sheet already fetches on demand from `/docs/help/[...slug]`. `src/server/docs.ts` (which already imports `allHelpCards`) gets `helpCardRoutes(): { id, routes }[]`. The authenticated layout calls it and passes the result to a client `HelpRoutesProvider`. This is build-time data, not request data.
- **The button stays where it is in PR 1:** `Std.Navbar` renders `<PageHelpButton />` (no props) at its far right on every page, and it renders nothing when no card matches. In PR 2 it moves into the layout navbar unchanged.
- **Flag-hidden cards behave as today:** the button shows and the sheet's fetch respects the flag. No flag evaluation in the button, since that would be request data.
- **Coverage stays as it is today.** Every `page.tsx` route under `(authenticated)` has to be covered by exactly one card's `routes` or be on an explicit opt-out list in the test. The opt-out list starts as exactly the pages that have no `<HelpButton>` today, so no page gains or loses Help in this change (method in Task 2).
- **`?help=<id>` and `<HelpSheet>` are unchanged.**

### Navbar and frame (#563)

From the spike (72f327cf, decisions 3, 5–7):

- **One navbar, rendered by the authenticated layout** inside `Std.SidebarInset` and **outside** its `<Suspense>`, so it stays up while a page loads. Pages stop rendering a navbar. `error.tsx`/`not-found.tsx` gain the ☰, which is fine.
- **Contents** (revised at checkpoint 1, replacing the spike's pinned ☰): everything sits in the page column, `max-w-5xl` centred. Left: ☰ then the AVUT logo. Right: notifications · theme · user menu · Help, with Help at the far end. No divider between ☰ and the logo. The ☰'s icon and the last icon (the glyphs, not the buttons) line up with the cards' edges, so the buttons overhang the column.
- **Page padding** (checkpoint 1): `Std.ScrollContainer` is `px-2 md:px-4` and reserves its scrollbar gutter on the right only (`stable`). The navbar's wrapper reserves the same gutter with the same padding, so its column matches the page whatever the scrollbar style.
- **The navbar carries no page data.** Its three request-dependent parts each sit in their own `<Suspense>`: the user menu (session, its existing skeleton), notifications (user-scoped `useQuery`), and `PageHelpButton` (`fallback={null}`: under `cacheComponents`, `usePathname()` suspends during prerender on routes with unknown dynamic params, i.e. every `/orgs/[slug]` page). #552 can then treat the shell as static frame with three small holes.
- **Sidebar:** the scope switcher moves up into `SidebarHeader` (`p-2`, no bottom border). The footer keeps only the What's-new version button. The account row is gone from the sidebar.
- **User menu:** a ghost icon button (`CircleUserRoundIcon`) opening the same menu, `size="md"`, `side="bottom"`, `align="end"` (spike's `user-menu.tsx`).
- **`nav/control-bar.tsx` is deleted** (unused).

### Breadcrumbs in the page (#559)

From the spike (89a1b0b8, 72f327cf decision 2):

- **`Saratoga.Breadcrumbs`:** ancestors only, every one a link (`{ label, href: Route }[]`), `text-xs`, on its own line directly above `Saratoga.Header` inside `Saratoga.Root`. The `<h1>` is the current crumb and isn't repeated. Shown in full at every width.
- **Trail contents: the record hierarchy, not the module** (user, checkpoint 1): today's `breadcrumbs` minus the first entry (the module, e.g. "Admin", "Skill Track", "D4H", "System Admin"; the sidebar already shows it) and minus the last (the page). A page at its module's top level (a module list like Personnel, Sessions, Teams) gets **no trail**. Trails end up 0–2 crumbs: Person → `Personnel`; Person History → `Personnel › Aaron Gray`; Session By Person → `Sessions › Session #2`; Skill matrix → `Reports`. This is the general rule; exceptions are decided case by case and listed here:
  - **Notes** keeps its "Notes" crumb on a note: in master-detail it's the way back to the list on phones, where the list pane is hidden.
- **Titles fit the trail** (user, checkpoint 1): History pages are "`<Record type>` History" ("Team History"); a related item's page takes the item's name (a team membership is titled with the person's name, not "Team Membership"). A record's sub-view drops the record's name from its title too (the session's checks page is "Skill Checks", not "Skill checks recorded in <name>").
- **Where the trail comes from, by shape:**
  - **Content component owns `Saratoga.Root`** (detail pages): it renders the trail, since it has the data (a record's name on its History page).
  - **A list component owns `Saratoga.Root` and `page.tsx` has the static crumbs** (~25 list pages: personnel, invitations, teams, users, rubbish bin, assessors, checks, sessions, skills, the system-admin lists, user-settings d4h/orgs, I3 bundles/templates, d4h-nag, d4h-today, …): the list component takes `breadcrumbs?: { label: string; href: Route }[]` and passes it to `Saratoga.Breadcrumbs`; `page.tsx` passes the static trail.
  - **History pages** render through `src/components/history/object-history.tsx` (21 importers): `ObjectHistory` takes the same `breadcrumbs` prop.
- **Ancestors with no link today:** "User Settings" (`d4h-access-token-content.tsx`, `organization-content.tsx`): dropped, there's no `/user/settings` page. "Access Tokens": dropped (it would link to the same page as the `D4H` crumb before it). Skill Package Builder "Groups"/"Skills" (group, skill and their History content): dropped, there's no index page for either. Any other link-less ancestor found on the sweep: dropped, and listed in the commit body.
- **Page split:** `page.tsx` renders `Std.ScrollContainer` around the content; `*-content.tsx` renders only the page body. 63 content components render their own `Std.ScrollContainer` today. All but two are a straight move. The two session recording pages (`session-by-person-content.tsx`, `session-by-skill-content.tsx`) use `className="flex"` for the approved empty state, so they render an inner wrapper instead. When the content suspends, it now lands in `ScrollContainer`'s own `<Suspense>` (spinner inside the scroll area, navbar and page background already up), not in `SidebarInset`'s. That's intended.
- **Pages without a Saratoga header:** proposed, to be settled at checkpoint 1:
  - **Glorious** matrices (four reports + I3 bundle matrix): the trail goes above `Glorious.Title` inside `Glorious.Header` (`Glorious.Breadcrumbs`, the same component), in both the scope-picker and the matrix branches. Glorious pages render no `ScrollContainer` (full height), and that stays.
  - **Hermes** (org and user notes, one shared `notes-breadcrumbs.tsx`): the trail goes in the detail pane above the note's title ("Notes" on a note; "Notes › <title>" on its History). The list pane and the index route have none. No `ScrollContainer`, as today.
  - **`Std.IndexPage`:** no trail, and no on-page logo (the navbar has it): just the title above the links (user, checkpoint 1). The sidebar is the way back up.
  - **`admin/organization/--update`** (a bare `Card`): the trail goes above the card.
  - **Playground** pages: no trail.
- **Phone width:** the trail shows every ancestor on one line, each truncating (`flex-nowrap`, `min-w-0`). Check at 390px.
- **`Std.Navbar`, `Std.Breadcrumbs` and the `breadcrumbs`/`actions` props are removed** once nothing uses them (Task 10).

### Title badges (#562)

- **Wrap:** `Saratoga.Title`'s title group is `flex min-w-0 flex-wrap items-center gap-x-2 gap-y-1` (spike). If the title and badges fit on one line, nothing changes. If not, the badges drop to a second row.
- **One status → badge map per status type,** in `src/components/ui/status-badge.tsx` as `<StatusBadge>` components that take the status value and render the right `Badge` variant and label, or `null` for the normal state. All 17 `Saratoga.Title badges=` call sites go through them.
- **Proposed mapping** (confirm at checkpoint 2), using #544's filled variants:
  - `RecordStatus` (person, team, membership, skill, group, bundle, template, …): Active → none, Archived → `warning`, Deleted → `destructive` ("Deleted"). Skill Track's `group-content.tsx` hard-codes "Archived" for any non-Active status today; it shows the real status now.
  - Session `SkillCheckStatus` (labels from `SKILL_CHECK_STATUS_LABELS`): Draft → none, Pending → `info` ("Pending review"), Include → `success` ("Approved"), Exclude → `warning` ("Excluded"), Deleted → `destructive`.
  - Skill Track package availability (`SkillPackage.isAvailable`, `package-content.tsx`): Withdrawn → `warning`, Deleted → `destructive`.
  - Skill Package Builder package publish state: Draft/Unpublished → `outline` (a normal working state).
  - D4H Nag rule: Paused → `warning`, Disabled → `outline`.
  - I3 forms (`form-shared.tsx`): Submitted → `success`.
  - System user: Banned → `destructive`.
  - D4H access token (free-string status, `isStatusOk`): OK/2xx → none, anything else → `destructive`.
- **Only title badges change.** Status badges in tables and rows (`d4h-member-status-badge.tsx`, `competency-status.tsx`) are out of scope.
