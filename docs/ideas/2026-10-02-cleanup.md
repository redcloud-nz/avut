### 3. Mount the Actions sheet on the session details page

The Actions sheet is `SkillTrack_SessionActionsSheet` in `src/components/skill-track/session-actions-sheet.tsx`, added by #323 (closed). It is mounted only in the navbar of the entry pages (`session-by-person-content.tsx:244-251`, `session-by-skill-content.tsx:268`). It is built for those pages:

- `mode` and `view` are required props (lines 92-100). `mode` highlights the current Record mode, and `view` drives the Skill Order radio group (lines 299-330), which has no meaning on the details page.
- Its sections are Configure (Personnel / Skills / Assessors), Record (By Person / By Skill), Activity (Recent checks) and Skill Order.

**Overlaps with the details page as it stands:**

| Sheet section | Already on the details page                                                                                            |
| ------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Configure     | The Contents card's change buttons (`session-contents.tsx:147` onward, via `useSessionConfigAction`)                   |
| Record        | The Record dropdown (`session-content.tsx:80-135`), including the same "Locked while the session is approved" handling |
| Recent checks | Nothing. This would be new on the details page                                                                         |
| Skill Order   | Not applicable                                                                                                         |

**Does the sheet conflict with the action menu?** In practice they split cleanly, but the names clash:

- The menu holds actions on the session as a record: History, Reopen, Delete, plus Edit and Review from items 1 and 2.
- The sheet holds tools for working inside the session: configure it, record into it, see recent activity.
- The clash is the label. Both read as "Actions" (the sheet's title is "Actions", lines 149 and 163). Two different "actions" surfaces on one page will confuse people.

**Technical catch:** the sheet hosts its own `SkillTrack_SessionConfigDialogs` (line 334), and the details page already mounts one (`session-content.tsx:209`). If both are on the page, the same `?action=change-*` param opens two copies of each dialog. One of them has to go, or the sheet needs a flag to skip hosting.

**Suggested shape:**

- Make `mode` and `view` optional. Without them, the sheet shows no current-mode highlight and hides Skill Order.
- Rename the sheet to something that isn't "Actions", such as "Session" or "Tools", with a different icon.
- Mount it in the details page navbar beside `HelpButton` (`session-content.tsx:73`).
- Drop the Record dropdown from the details page, since the sheet's Record section replaces it.
- Leave the Contents card's change buttons alone. They are where you look when reading the card.

**Issues:** filed as #354. Builds on #323 (closed). #211 (open) is an app-wide persistent right sidebar, which is a different concept.

### 4. Fix the "Select a …" prompt position on the entry pages

On `by-person` and `by-skill`, before anything is selected, the right pane shows an arrow and "Select a person to assess their skills." (or "Select a skill to assess."). It sits in the vertical middle of the pane. When the left-hand list is long, that puts the prompt far down the page, often below the fold, and the arrow points at the middle of the list rather than its top.

**Cause:** the two panes are a grid row, `grid-cols-1 lg:grid-cols-[1fr_auto_2fr]` (`session-by-person-content.tsx:311`, `session-by-skill-content.tsx:335`). Grid items stretch to the row's height, so the right pane is as tall as the list. The prompt is an `<Empty>` (`session-by-person-content.tsx:371-379`, `session-by-skill-content.tsx:477-485`), and `Empty`'s base classes include `flex-1 … justify-center` (`src/components/ui/empty.tsx:16`). It fills the tall pane and centres itself in it.

**Option A: pin the prompt to the top.** Stop the prompt growing at `lg`, so it sits at the top beside the start of the list. For example, add `className="lg:flex-none lg:justify-start"` on both `<Empty>`s, or `lg:self-start` on the right-pane wrapper. Below `lg` the panes stack, the up-arrow variant shows, and nothing changes. Optionally add `lg:sticky lg:top-…` so the prompt follows a long list as you scroll. This is two class changes.

**Option B: scroll the two columns independently.** At `lg`, size the page to the viewport and give each pane its own scroll region. Each pane is then only as tall as the screen, so the centred prompt lands mid-screen, and nothing about `<Empty>` needs to change. It also fixes a bigger annoyance: today the whole page scrolls as one, so scrolling down through a long skill list scrolls the person list away. With independent scrolling, the list stays in reach while you record.

What it takes:

- Both pages wrap everything in `Std.ScrollContainer` (`session-by-person-content.tsx:271-523`, and the same in `by-skill`), which gives one page-level scroll. At `lg` that has to become a bounded flex column instead. The precedent is `Glorious.Root` (`src/components/blocks/glorious.tsx:19-27`: `flex min-h-0 flex-1 flex-col`), which sits in place of `Std.ScrollContainer`.
- The title and the warning alerts (lines 273-310) stay fixed above the panes. The grid (line 311) becomes `lg:flex-1 lg:min-h-0`, and each pane gets `lg:min-h-0 lg:overflow-y-auto` with the app's scrollbar colours, as `Glorious.ScrollFrame` does (line 99).
- Below `lg` the panes stack, and keeping one page scroll is the right behaviour there. The independent scroll should only apply at `lg` and up.
- Selecting from the list sets state through an `onClick` (around line 350) and doesn't use URL anchors or `scrollIntoView`. Nothing relies on the page scroll position, but the right pane should scroll back to the top when the selection changes.

**Recommendation:** B is the better end state. A is a stopgap if B waits on #324.

**Issues:** deferred. Not part of the current cleanup; noted on #324 (open), whose two-pane retrofit is option B in general form. Option A is recorded there as the stopgap.

## App-wide

### 6. Mobile breadcrumbs: show the nearest ancestor, not a trail dropdown

Below `md`, the breadcrumb collapses to the current page's label plus a chevron. Tapping it opens a "Location" dropdown listing the whole trail (`src/components/blocks/std.tsx:71-118`). The ancestor crumbs and the leaf are hidden on mobile (`hidden md:block`, lines 124-137). In use it doesn't earn its space:

- The leaf label ("Checks", "By Person") repeats the page title.
- The menu is heavy for what is usually one destination: the parent.

**Change:** below `md`, show a single primary crumb: the nearest ancestor with an `href`, as a plain link. On a session subpage that's the session name, and on a person page it's "Personnel". Drop the leaf label and the trail dropdown.

- Deeper ancestors (Skill Track, Sessions) are no longer reachable from the breadcrumb on mobile. The sidebar covers them.
- It's a contained edit to `Breadcrumbs` (`std.tsx:63-140`). `BreadcrumbItem` (line 48) stays `{ label, href? }`.
- None of the ~100 call sites change. All of them go through `Std.Navbar`'s `breadcrumbs` prop or `Std.Breadcrumbs`, including the entry pages (`session-by-person-content.tsx:221`) and Notes (`src/components/notes/notes-breadcrumbs.tsx:44-57`).
- Open edge case: a page with no linked ancestor, such as a top-level page or the Notes list (`["Notes"]`). The suggested fallback is to show the leaf label as plain text, as happens today when there are no ancestors (line 136).

**Later:** the leaf's siblings (the other session subpages) would hang off the primary crumb as a dropdown, with Overview first and the current page marked. That would gather the session's scattered navigation (the Record dropdown, the Review link, and the History item from items 1 and 3) into one place. It's a separate, larger change: a client component, `usePathname()` current-page detection, and per-sibling permission gating. The plain-link change ships first and doesn't depend on it.

**Issues:** #202 (open, "Breadcrumb siblings + mobile collapse"). It records this design as of its 2026-09-22 revision. The current dropdown is its superseded "priority 1", and the notes say the plain-link primary crumb can ship on its own before siblings. Commented on #202 that the plain-link crumb ships first as its own PR.

### 7. Replace `<DL>` with `<DataItem>` on detail cards, with short values inline on mobile

Detail cards render their fields with `DL` / `DLTerm` / `DLDetails` (`src/components/ui/description-list.tsx`). Below `sm`, each label sits on its own line above its value. That suits long values (notes, lists) but wastes space for short ones like ID, Date and Status. On the session details card (`session-content.tsx:164-187`), five short fields take ten lines.

`DataItem` (`src/components/ui/data-item.tsx`) was introduced for settings rows in `25330010` (2026-09-24), where it replaced `DLActions`. It's already used in the user settings cards (`src/components/user/user-settings/user-profile.tsx:24` and three siblings). Each row is its own grid, with an optional `DataItemAction`. Moving detail cards onto it gives one row component across the app, and lets a detail row carry an action (such as the pencil from item 2) without a separate layout.

**What `DataItem` needs first:**

- **An inline variant.** Its mobile layout is `'title action' / 'value value'` (`data-item.tsx:21`), so the value still wraps below the label. Add a prop, such as `inline`, that keeps `'title value action'` at every width, with the value right-aligned or left-aligned after the label. Each call site decides per field: inline for ID, Date, Status and counts, stacked for notes and anything long.
- **Semantics.** `DL` renders a real `<dl>`/`<dt>`/`<dd>`; `DataItem` is all `<div>`s. Screen readers announce a description list as name/value pairs, which the divs lose. One option is a `DataList` wrapper rendering `<dl>`, with `DataItem` as the `<div>` group (valid inside a `<dl>`), `DataItemTitle` as `<dt>` and `DataItemValue` as `<dd>`. That keeps the semantics and the per-row grid.
- **A date value, inline on mobile.** `DLDateDetails` (`src/components/ui/description-list-date.tsx:24-44`) renders a `<dd>` with the timestamp on one line and the relative time ("3 days ago") muted below. It's used on the Created/Updated card of 15 pages (for example `session-content.tsx:195-204`). It needs a `DataItemValue` counterpart, or it can become one once `DataItemValue` renders a `<dd>`. Use the inline variant for these rows: label and timestamp on one line, relative time underneath in the value column. That takes the card on mobile from six lines to four without dropping anything. Wrap the timestamp in `<time dateTime>` while there, as `src/components/history/object-history.tsx:244-267` already does.
  - Inline fits for every date preset (`src/lib/datetime.ts:30-43`). The longest timestamp is `written` + 12-hour, "02 Oct 2026 10:14 PM", about 20 characters, which fits beside "Created"/"Updated" at 320px.
  - Rejected: relative time only, with the absolute timestamp in a tooltip. That's more compact, but phone users can't hover, so they would lose the exact time. Also rejected: timestamp and relative time on one line, which wraps at 320px for most presets.
- **Card spacing.** `DL` has `-my-3` to cancel its rows' padding inside `CardContent` (`description-list.tsx:21`); `DataItem` rows have `py-3` and no wrapper to offset it. A `DataList` wrapper can carry the same offset.

**Scope:** 25 files import `description-list`, mostly entity detail pages: personnel, teams, team memberships, users (org and system), organisations, D4H views, i3 templates, skill-package builder, the skill track catalogue and the session. It's mechanical once `DataItem` has the pieces above. Start with the session details card (combined with item 5), then do the rest in one sweep. Remove `description-list.tsx` at the end, and update `src/components/ui/README.md` (lines 55-57 and 86) to match.

**Issues:** filed as #351, including the Created/Updated card layout.

### 10. Render dates in the viewer's preferred format everywhere

The Joined column on `/user/settings/organizations` renders `new Date(ctx.getValue()).toLocaleDateString()` (`src/components/user/user-settings/organizations-list.tsx:68-74`). That's the browser's locale format, not the date format the user picked in Preferences, and it ignores their time zone.

`createdAt` here is the organisation membership's creation time, which is the date the user joined. So "Joined" is the right label, and the caution about `createdAt` posing as an external join date doesn't apply.

**Fix for this column:** `const { formatDate } = usePreferences();` (`src/hooks/use-preferences.tsx:51`) in `UserSettings_Organizations_List`, `cell: (ctx) => formatDate(ctx.getValue())`, and add `formatDate` to the `useMemo` deps.

**The wider problem:** `formatDate`/`formatDateTime` (`src/lib/datetime.ts:72-91`) fall back to the default preferences when no `prefs` argument is passed. The doc comment there (lines 60-67) says most call sites are still in that state, and that threading preferences into table columns and `FieldValue` was deliberately left for a separate change. That change hasn't happened. Call sites that ignore the preference today:

- **Raw `toLocale*`:**
  - `src/components/user/user-settings/d4h-access-tokens-list.tsx:78`
  - `src/app/(wrapper)/(authenticated)/orgs/[slug]/admin/d4h-access-tokens/d4h-access-tokens-list.tsx:77`
  - the Joined column above
- **Kaga table columns:**
  - `src/components/admin/invitations/invitations-list.tsx:82`
  - `src/components/system/admin/organizations/organizations-list.tsx:110`
  - `src/components/system/admin/users/users-list.tsx:102`
  - `src/components/skill-track/sessions-list.tsx:75`
- **Created/Updated cards written out by hand** rather than with `DLDateDetails`:
  - `src/components/admin/personnel/person-content.tsx:106,114`
  - `src/components/skill-track/catalogue-package-content.tsx:150,157`

  Item 7's migration would also catch these.

- **Other components:**
  - `src/components/skill-track/session-content.tsx:172` (the session date)
  - `src/components/skill-track/review-checks-dialog.tsx:233`
  - `src/components/skill-track/reports/person-competency-report.tsx:334`
  - `src/components/skill-track/reports/report-cell-popovers.tsx:225,238`
  - `src/components/controls/date-picker.tsx:76`
- **`FieldValue`** (`src/components/ui/field-value.tsx:92-113`), which every caller inherits.

**Change:** do the organisations Joined column now (it's the one that prompted this), then sweep the rest. Every client call site takes `formatDate`/`formatDateTime` from `usePreferences()`, and server components pass `getDisplayPreferences()` (`@/server/display-preferences`). Once nothing relies on the default, consider making `prefs` required so a new call site can't silently ignore the preference. That would leave `DEFAULT_DISPLAY_PREFERENCES` for the settings preview and tests only.
